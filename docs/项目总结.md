# Aether Deep Agent Service 项目总结

## 1. 项目介绍

`aether-deep-agent-service` 是 Aether 平台的 Python 异步 Deep Agent 执行服务。它不直接服务浏览器或终端用户，而是由 Java Admin 创建运行请求、签发工具委派令牌、接收回调事件并保存审计信息。

服务面向需要多步骤推理、知识证据分析、MCP 工具调用及人工介入的任务，负责将一次任务从需求补充、方案规划、执行、暂停恢复到结果回传的完整流程落地。

项目当前版本为 `0.1.0`，要求 Python `3.11+`。

## 2. 项目定位与边界

### 服务负责的内容

- 校验 Java Admin 发起请求的 HMAC 签名。
- 解析 Agent 模型配置，并在必要时从 Java Admin 获取 OpenAI 兼容模型的地址和密钥。
- 检查任务信息是否完整，必要时通过 `ask_user` 发起用户补充。
- 生成任务方案文档、执行步骤和用户可见的计划投影。
- 创建并运行 LangGraph/Deep Agents 图。
- 按请求允许范围加载并调用 MCP 工具。
- 处理工具审批、用户问答、计划审批、暂停和恢复。
- 持久化运行状态、交互状态、计划检查点和待投递回调。
- 通过签名回调向 Java Admin 实时推送运行过程和最终结果。

### 服务不负责的内容

- 不直接维护浏览器会话或前端页面。
- 不自行检索平台知识库，只使用 Java Admin 随请求下发的证据片段。
- 不签发工具访问令牌，仅透传 Java 下发的短期委派令牌。
- 不持久化从 Admin 获取的模型 API Key。
- 不将任意 MCP 工具直接暴露给模型，只加载请求白名单中的工具。

## 3. 技术框架

| 分类 | 技术 | 用途 |
| --- | --- | --- |
| Web 框架 | FastAPI | 提供健康检查、运行创建、查询、暂停、取消和恢复接口。 |
| ASGI 服务器 | Uvicorn | 启动异步 HTTP 服务。 |
| Agent 框架 | Deep Agents | 创建受工具和系统提示词约束的执行 Agent。 |
| 图执行与检查点 | LangGraph | 执行可中断的 Agent 图，并支持持久化恢复。 |
| 模型接入 | LangChain、langchain-openai | 初始化聊天模型、流式输出和 Token 用量统计。 |
| MCP 集成 | langchain-mcp-adapters、MCP | 通过 Streamable HTTP 加载并调用 Java 委派的工具。 |
| 数据访问 | SQLAlchemy 异步 ORM | 持久化运行、检查点、待处理交互和回调发件箱。 |
| PostgreSQL 驱动 | asyncpg、psycopg | 分别用于业务存储与 LangGraph PostgreSQL 检查点。 |
| 配置管理 | pydantic-settings | 从环境变量和 `.env` 加载、校验服务配置。 |
| HTTP 客户端 | HTTPX | 调用 Java Admin 的模型配置和回调接口。 |
| 测试 | pytest、pytest-asyncio | 覆盖应用、执行器、回调、恢复和签名逻辑。 |
| 依赖与构建 | uv、Hatchling | 管理依赖、锁定版本及构建 Python 包。 |

```text

  |-- 需求分析与方案规划

  |-- MCP 工具适配层

  |     `-- 回调发件箱
```

| 执行器 | `executor.py` | 分析需求、生成方案、构造 Agent、加载 MCP 工具、执行图并处理人工中断。 |

| 配置模块 | `settings.py` | 定义环境变量、默认值和参数边界。 |

## 5. 核心功能

### 5.1 需求完整性分析

任务开始前，执行器会调用模型分析任务是否具备可执行条件。

- 简单寒暄和自我介绍类问题跳过需求补充，直接进入后续回答流程。
- 对确实缺失且无法从任务描述或知识证据推导的信息，生成 1 至 4 个结构化选择题。
- 每题要求提供 2 至 4 个具体选项，同时允许自由文本补充。
- 缺失信息时发布 `ask_user.required` 事件，运行进入等待状态，不会盲目生成计划。

### 5.2 方案规划与审批

服务先生成面向用户展示的规划文档，再生成可执行任务步骤。

规划文档可包含以下内容：

- 任务标题和目标。
- 已知背景与约束。
- 执行方案和原因。
- 1 至 6 个具体、有序的执行步骤。
- 风险与注意事项。
- 可验证的验收标准。

当请求的 `plan_approval_required` 为 `true` 且模型判定任务复杂时，服务会：

1. 发布初始 `plan.updated` 事件。
2. 持久化计划审批交互。
3. 发布 `plan.approval.required` 事件。
4. 等待用户批准或提交计划反馈。

用户反馈方案后，服务会重新生成方案文档和任务步骤，并再次请求审批。简单任务不需要审批，可直接执行。

### 5.3 执行计划与动态重规划

服务维护独立于 LangGraph 内部状态的用户可见计划投影。

- 初始计划会以 `plan.updated` 事件发布。
- 模型调用 `write_todos` 时，系统把最新 `todos` 映射为计划步骤并覆盖原投影。
- 工具完成或失败时，可依据观察结果调用模型调整剩余步骤。
- 已完成步骤会在重规划中保留，新的待办步骤使用新的标识。
- 完成运行后，计划会被标记为完成并再次发布。

计划投影只用于展示、审计和恢复，不会直接重放有副作用的工具调用；真正的下一步执行仍由 LangGraph 持久化状态决定。

### 5.4 MCP 工具调用与审批

服务通过 `MultiServerMCPClient` 访问 MCP Streamable HTTP 服务。

- 仅加载 `allowed_tools` 白名单中的工具。
- 将 Java 签发的 `delegation_token` 作为 Bearer Token 传给 MCP 服务。
- 内置 `ask_user` 工具用于补充业务信息，不能被当作工具审批使用。
- 工具审批策略由 `tool_approval_policy` 控制：

| 策略 | 行为 |
| --- | --- |
| `ask` | MCP 工具调用在图中断，等待用户批准或拒绝。 |
| `risky` | 服务保留中断，由 Java 侧按单项风险评估并可自动恢复低风险批次。 |
| `never` | Java 对本次运行显式授权，MCP 工具不因审批中断；`ask_user` 仍会等待用户回答。 |

### 5.5 流式遥测与运行事件

`RunTelemetryHandler` 监听 LangChain 回调并发布以下运行信息：

- 工具启动：`tool.started`。
- 工具完成：`tool.completed`，包括输出摘要与耗时。
- 工具失败：`tool.failed`，包括错误与耗时。
- 文本增量：`message.delta`。
- 待办同步：`todos.updated`，用于更新用户可见计划。
- 步骤验证：`step.verified`。

对于有执行计划的任务，系统要求模型在最终回复中为每个步骤输出 `[STEP_VERIFIED]` 标记。服务提取这些标记生成步骤验证事件，并在持久化最终结果前移除标记，避免内部执行协议泄漏给最终用户。若模型没有输出标记，则用工具输出摘要作为验证结论兜底。

### 5.6 引用与知识证据

每个请求可以携带多个 `knowledge_sources` 证据片段，包含文档名称、内容、引用编号、分块标识等信息。

- Agent 系统提示词约束模型只能使用下发证据，不得声称使用了未提供的来源。
- 服务把证据格式化为带引用编号的上下文。
- 最终结果中引用的来源会被筛选并随 `run.completed` 回调返回。
- 服务会将半角数字引用如 `[1]` 规范为全角格式 `【1】`，以便 Java 审计和 Dashboard 锚点一致。

### 5.7 暂停、恢复与故障恢复

服务支持三类中断状态：工具审批、用户补充信息和计划审批，同时支持显式暂停和服务重启恢复。

- 工具审批与 `ask_user` 交互会保存到 `deep_agent_pending_interaction`。
- 计划、文档、复杂度判断和运行阶段会保存到检查点表。
- 运行暂停后，可从 LangGraph 的持久化线程检查点继续执行。
- 服务启动时会将此前处于 `QUEUED` 或 `RUNNING` 的运行标记为 `PAUSED`。
- 恢复时优先重现仍待处理的交互，防止没有用户决策时盲目恢复图执行。

## 6. 持久化设计

`RunStore` 使用 SQLAlchemy 异步 ORM 管理以下数据表：

| 表 | 用途 |
| --- | --- |
| `deep_agent_run` | 保存运行请求、状态、最终结果、错误信息、会话与任务标识。 |
| `deep_agent_checkpoint` | 保存递增编号的状态快照，包括计划、阶段、方案文档和复杂度判断。 |
| `deep_agent_pending_interaction` | 保存当前等待用户处理的审批、提问或计划交互。 |
| `deep_agent_callback_outbox` | 保存尚未确认投递的回调事件。 |
| `deep_agent_schema_migration` | 仅在 PostgreSQL 中记录已执行的 SQL 迁移版本。 |

生产环境使用 PostgreSQL。`AsyncPostgresSaver` 负责 LangGraph 的持久化检查点；业务状态由 `RunStore` 单独保存。SQLite 和 `InMemorySaver` 仅用于轻量测试场景。

## 7. 回调可靠性

每个向 Java Admin 发送的事件都会先写入回调发件箱，再进行网络投递。

1. 生成唯一的 `event_id` 和发生时间。
2. 将事件写入 `deep_agent_callback_outbox`，初始状态为未投递。
3. 使用 HMAC 签名向 Java Admin 发送回调。
4. 成功后将事件标记为已投递。
5. 遇到网络错误、HTTP `429` 或服务端 `5xx` 时，按线性退避重试。
6. 服务重启时，重新投递未完成事件。

该机制使回调具备至少一次投递语义。Java Admin 应依据 `event_id` 实现幂等消费。

## 8. HTTP 接口

除 `/health` 外，所有接口均依赖 HMAC 请求签名验证。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/health` | 返回 `{"status":"ok"}`，用于存活探针。 |
| `POST` | `/v1/runs` | 创建或幂等获取一次运行。 |
| `POST` | `/v1/sessions/{session_id}/tasks` | 按会话创建任务的别名接口。 |
| `POST` | `/v1/runs/{run_id}/cancel` | 取消运行。 |
| `POST` | `/v1/runs/{run_id}/pause` | 请求暂停运行。 |
| `GET` | `/v1/runs/{run_id}` | 查询运行状态与最新检查点编号。 |
| `GET` | `/v1/sessions/{session_id}` | 查询会话最近一次任务的状态。 |
| `POST` | `/v1/runs/{run_id}/resume` | 提交审批决策、用户答案或计划反馈并恢复运行。 |
| `POST` | `/v1/sessions/{session_id}/tasks/{task_id}/resume` | 按会话和任务标识恢复最近一次运行。 |

### 运行创建请求关键字段

| 字段 | 含义 |
| --- | --- |
| `run_id` | 本次执行尝试的唯一标识，用于幂等创建与审计。 |
| `user_id`、`agent_id`、`conversation_id` | Java Admin 所属主体与会话标识。 |
| `session_id`、`task_id` | 可选的持久化会话及业务任务标识。 |
| `task` | 用户任务正文。 |
| `task_state` | 计划、文档等可恢复的任务状态投影。 |
| `system_prompt` | 上游提供的系统提示词。 |
| `conversation_memory` | 最多 24 条持久化会话消息。 |
| `knowledge_sources` | 供模型使用的知识证据片段。 |
| `allowed_tools` | 本次运行允许加载的 MCP 工具白名单。 |
| `delegation_token` | Java 签发、传递给 MCP 服务的短期令牌。 |
| `tool_approval_policy` | 工具审批策略：`ask`、`risky` 或 `never`。 |
| `plan_approval_required` | 是否对复杂方案启用执行前审批。 |
| `timeout_seconds` | 可选运行超时；未提供时使用服务默认值。 |

## 9. 安全设计

### HMAC 请求签名

调用方和回调接收方使用相同的 HMAC-SHA256 签名规则：

```text
payload = UTF-8(timestamp) + b"." + request_body
signature = HMAC-SHA256(shared_secret, payload)
```

涉及的请求头如下：

| 请求头 | 用途 |
| --- | --- |
| `X-Aether-Key-Id` | 标识调用方使用的服务密钥。 |
| `X-Aether-Timestamp` | Unix 秒级时间戳。 |
| `X-Aether-Signature` | 对时间戳和原始请求体计算的 HMAC-SHA256 十六进制摘要。 |

服务要求时间戳与当前时间的差值不超过 300 秒，以降低重放攻击风险，并使用常量时间比较验证签名。

### 模型与工具凭据

- 模型 API Key 仅通过签名内部接口从 Java Admin 获取，只缓存在进程内存中。
- MCP 调用只透传短期 `delegation_token`，不保存静态工具 Token。
- 模型只能访问请求提供的证据和允许使用的工具。
- 生产环境应将 `AETHER_DEEP_AGENT_SHARED_SECRET` 和模型 API Key 放入密钥管理系统或未提交的 `.env` 文件中。

## 10. 配置说明

配置通过环境变量加载，所有服务专属变量均以 `AETHER_DEEP_AGENT_` 为前缀。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `AETHER_DEEP_AGENT_SHARED_SECRET` | 空字符串 | 请求和回调 HMAC 共享密钥，生产环境必须配置。 |
| `AETHER_DEEP_AGENT_KEY_ID` | `deep-agent-v1` | 服务密钥标识。 |
| `AETHER_DEEP_AGENT_CALLBACK_BASE_URL` | 空字符串 | Java Admin 内部地址。 |
| `AETHER_DEEP_AGENT_DATABASE_URL` | PostgreSQL 开发连接串 | SQLAlchemy 异步数据库地址。 |
| `AETHER_DEEP_AGENT_MODEL` | 空字符串 | 默认 LangChain 模型标识。 |
| `AETHER_DEEP_AGENT_MCP_URL` | 空字符串 | MCP Streamable HTTP 服务地址。 |
| `AETHER_DEEP_AGENT_MAX_STEPS` | `12` | 默认最大步骤数。 |
| `AETHER_DEEP_AGENT_RUN_TIMEOUT_SECONDS` | `600` | 默认运行超时秒数。 |
| `AETHER_DEEP_AGENT_CALLBACK_TIMEOUT_SECONDS` | `10.0` | 单次回调 HTTP 超时秒数。 |
| `AETHER_DEEP_AGENT_CALLBACK_MAX_RETRIES` | `3` | 回调最大重试次数。 |
| `AETHER_DEEP_AGENT_CALLBACK_RETRY_BACKOFF_SECONDS` | `1.0` | 回调线性退避的基础秒数。 |
| `OPENAI_API_KEY`、`OPENAI_BASE_URL` | 由模型提供商决定 | OpenAI 兼容模型配置。 |
| `ANTHROPIC_API_KEY`、`GOOGLE_API_KEY` | 空字符串 | 其他模型提供商的密钥。 |

`.env.example` 提供 Docker 共享网络、Java Admin、MCP、PostgreSQL 及模型配置的示例。

## 11. 本地开发与测试

### 前置条件

- Python `3.11+`。
- `uv`。
- 可用的 PostgreSQL、Java Admin 和 MCP 服务用于端到端运行。

### 安装和启动

```powershell
uv sync
$env:AETHER_DEEP_AGENT_SHARED_SECRET = "change-me"
$env:AETHER_DEEP_AGENT_CALLBACK_BASE_URL = "http://localhost:8080"
$env:AETHER_DEEP_AGENT_MCP_URL = "http://localhost:8000/mcp"
$env:AETHER_DEEP_AGENT_MODEL = "openai:gpt-4.1-mini"
$env:OPENAI_API_KEY = "..."
uv run aether-deep-agent-service
```

默认监听地址为 `0.0.0.0:8010`，健康检查地址为 `GET /health`。

### 测试

```powershell
uv run pytest -q
```

测试覆盖签名计算、回调重试、应用接口、执行器规划和工具逻辑、步骤验证、暂停恢复、回调重投与计划审批流程。

## 12. Docker 部署

项目提供 `Dockerfile` 和 `docker-compose.yml`。

- 镜像基于 `python:3.11-slim`。
- 使用 `uv` 和锁文件安装生产依赖。
- 默认暴露 `8010` 端口。
- Compose 服务名为 `deep-agent`，容器名为 `aether-deep-agent`。
- 服务加入外部共享网络，以访问 Java Admin、MCP 和 PostgreSQL。
- 容器通过 `/health` 执行健康检查。

启动命令：

```powershell
docker compose up -d --build deep-agent
```

独立部署时，必须将数据库地址、共享密钥、Java Admin 地址、MCP 地址和模型密钥替换为目标环境配置。完整平台部署应使用 Java 项目提供的统一编排文件。
